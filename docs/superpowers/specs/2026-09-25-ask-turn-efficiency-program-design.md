# Ask-your-docs turn efficiency: fewer turns to the needle, no budget-exhausted apologies, completeness defined and measured

## Problem Statement

The owner's complaint: the ask-your-docs chat agent calls too many tools, and sometimes reaches its turn cap without a grounded answer. The program has three goals: reach the Needle in fewer Turns; check that the Needle is complete before stopping; never end a question on LangGraph's canned "Sorry, need more steps to process this request." reply. Vocabulary follows `CONTEXT.md`: Needle, Turn, Turns-to-answer, Budget exhaustion, Finalized answer, Turns after needle, Needed call, Needless call, Pointer, Pointer bundle. Where this document says "gold" it means a dataset's gold label; the location it names is the Needle.

Four symptoms, with the evidence from the 2026-09-24/25 analysis (`final_report.md`, the 10-question live reproduction under `repro/`, and the 2026-09-15 before/after run), re-checked against `origin/main` at `87ac5d5b`:

1. **Over-exploration.** Ten open-ended chat questions on `example_needle` with the owner's serving config (`architecture: auto`, bare question, no scaffold) took 5.7 Turns and 8.9 calls per question, about 46k tokens in each (`repro/out/summary.json`; per question 4–8 Turns, 5–13 calls). The causes are text the model is handed. The served prompt asks for an Example snippet and points at `get_symbol` for it (`python/pydocs_mcp/harness/core/prompts/system_v2.j2:17-21`; q04's card→context→source chain, 5 of its 8 calls), tells the model to issue every "Together:" pointer in one turn (v2:28-30, so an 8-hit search prescribes up to 16 calls), keeps a card-first rule the model ignores 26/35 times (v2:38-39), and the `get_overview` description says "first call on an unfamiliar project" (`python/pydocs_mcp/defaults/descriptions.md:18`; `get_overview` opened 7/10 questions, 5 in parallel with the first search). The only stop rule in the repo lives in a skill the chat page never loads (`app.py:261-274` → `prompt_assembly.py:85-86` returns `None`). Tool output sends the model back for what it already had: class and module source views ending in `[lines a-b not in the index]` plus "read … for the full text" (15 of 35 `get_symbol` calls; 3/10 questions did source→`read_file` on the same file), heading hits whose source pointer returns the same prose (q03, q09), `get_context` giving body slots to zero-length builtins and failing a whole batch on one bad target (q05, q07), and `grep path=<file>` never matching (16/16 zeros, 2 in q02). The analysis first classed 35 of 89 calls as Needless; review showed at least four were load-bearing for completeness, so the honest addressable count is 25–30, concentrated in a few patterns.

2. **Budget exhaustion with no answer.** It did not occur on current code — no repro question reached 12 Turns (the maximum was 8) and 0/30 tasks in the last eval arm ended on the sentinel — but the mechanism is real and silent. `turn_budget.py:24-30` sets `recursion_limit = 2 × max_agent_turns`, always even, so on the 12th call the prebuilt agent replaces any tool-calling reply with the 47-character apology (langgraph 1.2.8, `chat_agent_executor.py:631,689,716`); no `GraphRecursionError` is raised, so `TurnBudgetExceededError` (`binding.py:467-468`), the eval sentinel and the UI label (`activity_labels.py:66`) are dead code on the prebuilt path, the only unit test passes by faking a graph that raises (`test_binding.py:263-300`), `ask()` stores the apology in history (`agent.py:474-484`), reformulation rewrites against it, and the 12th call's tokens go unmetered (`model_usage.py:133-137`). The scratch repro's own `budget_exhausted` flag keys on `GraphRecursionError` too, so it can never read true; the Turn counts are the evidence. The one recorded instance is on the pre-2026-09-15 code the owner's two UIs (ports 8512/8513, started 2026-09-12 from a deleted worktree) still run. The only 12-Turn run on current code answered on call 12 of 12: a near miss, not a clean bill.

3. **Slow first hit.** Not the bottleneck: the Needle appeared in a turn-1 result in 27/29 repoqa tasks, first at call 1.24 on average, and the model's own queries reach function-level recall@10 of 0.913. Every retrieval proposal was refuted, one by direct measurement (hybrid RRF −0.33 recall@1 against dense).

4. **Incomplete needle.** The real open problem: 3/10 multi-site chat answers were incomplete (q01 missed the second identical mask in `pipeline.py:116-126`; q08 missed four literal defaults; q03 said "full checklist" and missed `README.md:97-106`), and 4/30 repoqa answers were plausible-but-wrong stops with 5–9 Turns unused. Nothing defines "complete", the answer text is never persisted (`before_after_arm.py:312` stores only `answer_chars`), Needle-reached sits at 29/30 so it cannot see a dropped location, and the deterministic grounding gate proposed for it fired false positives on every case it was designed to catch.

Limits of the evidence: one chat model, `qwen/qwen3.8-27b`, for both the repro and both eval arms — but not at one setting: the eval arms ran the Q5 block (thinking, temperature 1.0, top_p 0.95, max_tokens 16384, via `--llm-block`), while the repro config carries no `params` block and no `provider` (`repro/config.yaml`), so every param defaulted to `None` (`retrieval/config/ask_your_docs_params_models.py:99-102`, provider `auto` at :40) and the repro ran at the endpoint's defaults. The A/A noise floor at the Q5 pin has not been measured. One 169-file project-only corpus (73 files indexed under the default project extensions with `.claude` excluded); an easy single-needle repoqa split; n=10 single-sample chat questions. Every number is directional. The measurement stack cannot see symptoms 2 or 4 today, so the first steps are measurement scaffolding. The program stays on this one chat model and answers the corpus limit with one larger-corpus check (Q49): pydocs-mcp itself indexed with its runtime dependencies, plus 10 questions the owner writes, run before symptom 1 is declared solved.

A second, structural fact shapes where the program's text may live. The chat page loads no search-guidance skill today (`app.py:252-274` builds through `build_agent` with no `task_name`; `prompt_assembly.py:85-86` returns `None`), so the only policy the chat model reads is the system template plus the tool descriptions. The platform vision (`docs/superpowers/specs/2026-07-26-retriever-centric-harness-platform-design.md`) puts transferable search policy in the trainable three-tier skill document — `BACKBONE` / `TASK_HEAD:<task>` / `HARNESS_TASK_HEAD:<harness>.<task>` (`python/pydocs_mcp/harness/core/skills/search_guidance_seed.md`) — and forbids per-task tool-description variants (ADR 0005). Both the system template and the skill document are already trainable surfaces (`ACTIVE_SYSTEM_PROMPT_TEMPLATE`, `harness/core/prompt_surfaces.py:66-79`, seeds the optimizer's `ask_prompt` artifact), so this program does not choose between them: the ladder moves the template, and the seed restatement rides one experiment (see "How this seeds the multitask optimizer").

## Solution

The levers are prompt text and tool output, not a new agent architecture, not new tools, not retrieval. A cumulative ladder of nine steps (0–8), each its own ticket, each measured against the previous accepted state, lands: measurement scaffolding first (chat trace persistence; a vendored chat slice with code-authored gold, 30 held-out questions of which 10 are reserved for final confirmation only, and a runner whose output the acceptance verb reads as an arm; a measurability slice, split into an eval half and a product half, that persists answers and books every unanswered outcome honestly); then an architecture-agnostic finalize path that turns a budget-exhausted question into a Finalized answer made without tools, ending with a `Not confirmed:` line; four tool-hygiene fixes with ADR 0023 ratified by four amendments; a slim `system_v3` that removes only call-inducing rules, adds the two Q40 clauses, absorbs #323 and rewords two lines of `descriptions.md`; gap-free class and module source views; the decision-protocol plumbing, as ordered sub-PRs, that makes same-commit variant arms and multi-location slices runnable; and, last, the completeness definition and stop test as a separate measured arm whose channel is chosen after the `guidance_task` experiment reports. Steps 1, 2 and 7 are split into ordered sub-PRs (Q46's shape; 1a/1b, 2a/2b, 7a–7e); every PR carries its own CHANGELOG bullet.

Answers are stored and scored by code first (needle cited), then by a tiered judge: TypeSafe Jev (`jev-1.13`, pinned, via OpenRouter, behind an owned plain-HTTP client) scores every answer; inside its review band the answer goes to an escalation judge of a different family, cached and capped; both are fitted to an alignment set labelled blind by two labellers of two further families and adjudicated by the owner. Reference answers for the 60 repoqa-qa tasks and the 40 chat questions are written once from ground truth by `anthropic/claude-opus-5.5:batch`, code-checked, spot-checked or ratified by the owner, frozen, and never used to produce a calibration answer (Q55, Q57, Q56′). Four contested items run as experiments whose PRs close unmerged if they lose; the `guidance_task` experiment doubles as the bridge to the multitask optimizer — its $0 candidate seed restates v3's rules in the skill layers the platform vision names, and its winning PR is the migration (B1). One $0 PR outside the ladder brings `SERVER_INSTRUCTIONS` into agreement with v3 (B5). Everything stays behind the frozen nine-tool surface, the tool descriptions stay one shared document (B6), and the spend ceiling is $35 with a stop-and-ask at $25 (Q54).

## User Stories

2. As a chat user, I want a question that exhausts its budget to end with an answer that names what it could not confirm, never with "Sorry, need more steps to process this request."

4. As a chat user, I want the assistant to answer "where are all the places" questions with every site, so that a multi-site answer is complete.
5. As a chat user, I want a class or module source view to show the real lines, docstrings, constants and decorators included, so that the assistant does not re-read the file.

10c. As the owner, I want one larger-corpus check on pydocs-mcp with its runtime dependencies, with my own 10 questions, before anyone tells me symptom 1 is solved (Q49).

## Implementation Decisions

### Constraints that shape everything

- **The nine-tool MCP surface is frozen** (`docs/tool-contracts.md`, ADRs 0001–0004). No tenth tool, no new parameter, no new envelope field. Every setting below is YAML under `AppConfig`, an eval-side YAML, or a code constant, never a tool argument.
- **Single source for defaults.** Every default lives once: a pydantic `Field(default=…)` or a `_DEFAULT_X` constant, restated in `default_config.yaml` (or the eval's own YAML) only for user-facing clarity. Closed vocabularies are `StrEnum` classes with UPPER_SNAKE members; Protocols carry no `Protocol` suffix (`FilterAdapter`, `UnitOfWork`, `HarnessRunner` precedents). Every external call has a timeout and a bounded retry count. Optional dependencies are null objects, not `X | None`.
- **Prompt versions are byte-pinned.** `system_v2.j2` and `system_v1.j2` are never edited (`harness/core/prompts/__init__.py:14-17`; `harness/ask_your_docs/prompts/__init__.py:29-30`); a new version is a new file plus a flip of `ACTIVE_SYSTEM_PROMPT_TEMPLATE` (`harness/core/prompt_surfaces.py:66`), a regenerated seed (`benchmarks/src/pydocs_eval/optimize/artifacts/ask_prompt_seed.md`) and a golden.
- **ADR 0023 is still Proposed** (`docs/adr/0023-…md:3-7`; ten `pending owner ratification` markers in `docs/tool-contracts.md` at lines 59, 64, 96, 117, 223, 306, 310, 317, 373, 459). Contract wording changes in this program ride its ratification (Q32). ADR 0025 is free (`docs/adr/` ends at 0024; the latest release is 0.8.1, `CHANGELOG.md:118`).
- **The eval's import floor.** `trajectory/` keeps a zero-`pydocs_mcp` floor (`trajectory/token_accounting.py:44-48`) and the new `judge/` package is stdlib plus httpx by design; `campaign/` and `optimize/ask_binding.py` already import `pydocs_mcp` function-locally (`before_after_corpora.py:343`, `index_cache.py:41`, `ask_binding.py:55`). Product literals the floor-keeping packages need (`BUDGET_EXHAUSTED_REPLY`, `NOT_CONFIRMED_LABEL`, both introduced by step 2b) are mirrored there as `ASK_*` constants landed by step 2a, never imported; each mirror has a parity test that reads the product attribute with `getattr` and `pytest.skip`s while it is absent (an `importorskip` would not do: it skips on a missing module, not a missing attribute, and 2a merges before 2b).
- **Spend.** OpenRouter throughout, pinned to the 2026-09-15 block (Q5): chat `qwen/qwen3.8-27b` in thinking mode (`provider: openrouter`, `thinking: auto`, temperature 1.0, top_p 0.95, max_tokens 16384) from `benchmarks/configs/ask_openrouter_qwen3_8_27b_llm.yaml`; embeddings `qwen/qwen3-embedding-4b` at 2560 dimensions from `benchmarks/configs/ask_openrouter_qwen3_4b.yaml`; `OPENROUTER_API_KEY` from the base repo's `.env`, never printed. The pinned block file is also the single source of the chat model's timeout, retry count and upstream provider route (Q48(c), Q48(d)): `llm.timeout_seconds`, `llm.max_retries` and `llm.provider_routing` are keys of that file, wired by step 2b, never module constants. Ceiling $35, stop-and-ask at $25 (Q54, replacing the $20/$15 pair), a $15 sub-budget for alignment labels, a $2 cap on in-band escalations (Q52), spend read at OpenRouter after each step, owner's go before every paid rung (Q16). One A/A pair (two arms, same commit, same settings) before the first comparison; its ~120 answers are also the pool the judge is aligned on (Round 5b Fact). The cost ledger under Measurement is the running total; the drop order at $25 is: one pointer-density variant first, then the Members and `guidance_task` experiments, then the cap-5 arm, then the seed variant (Q39 as amended in Round 5).
- **Three model families, kept apart** (Round 5d). Qwen is the agent under test; Anthropic (`anthropic/claude-opus-5.5:batch`) writes the reference answers from ground truth; OpenAI (`openai/gpt-6-astra:batch` as one alignment labeller, `openai/gpt-6-luna` as the escalation judge) and TypeSafe Jev judge. Opus also labels the alignment set as the second blind labeller (Q58), which is why reference-based labels count only when Astra independently agrees. No judge grades text written by its own family. The optimizer keeps its own `claude-sonnet-5` rubric judge (Q23); none of these roles runs inside the optimizer.
- **Cumulative ladder** (Q6, Q30): steps 0–8 in order, each measured against the previous accepted state; one ticket and one PR per step, each PR with its own CHANGELOG `[Unreleased]` bullet (Q8/Q17; the ladder serializes merges so bullets do not conflict). Steps 1, 2 and 7 are split into ordered sub-PRs (Q46's shape: 1a dataset then 1b held-out set; 2a eval then 2b product; 7a–7e in the order step 7 lists), every sub-PR with its own bullet and its own ticket, merged in that fixed order — never changelog-free code PRs with a trailing entry PR. The one sub-PR that leaves ladder position is 7a (the compare verb, `holm_adjust`, the cost model): it changes no measured behaviour and it is the instrument every acceptance below reads, so it lands as soon as 2a has merged, before step 3 is measured; 7b–7e keep their place after step 6. Experiments follow Q11: a losing PR is closed unmerged, its table recorded in the umbrella issue; nothing merges behind a switch that stays off — so an experiment PR ships its knob off (or its step unregistered by default) plus an overlay arm, and the winning PR flips the default. The two opt-in, default-off knobs the owner explicitly accepted (Q31 chat trace persistence; Q38 in-harness Jev) are owner exceptions for observability and a late experiment, not tuning switches.
- **What may and may not move** (bridge, item 8). Acceptable fingerprint moves, each recorded in the umbrella issue: `AskPromptArtifact.fingerprint` twice (the v3 flip in step 5, the v4 slim in the `guidance_task` winning PR); `SearchSkillArtifact`'s fingerprint once (seed adoption in that same winning PR); `current_artifact_hash()` plus the tool-docs fingerprint on every `descriptions.md` edit (steps 4 and 5, the B5 PR). No optimizer ledger is committed, so a re-key costs nothing today. Must not move: the nine-tool surface, `DELIVERED_SECTION_CHANNELS` and `delivery_map_digest()` (`harness/ask_your_docs/binding.py:128-157`), `HARNESS_NAMES` / `TASK_NAMES` (`harness/core/skill_artifact_loader.py:71-72`), and the freeze-pool digests (`tests/fixtures/goldens/ask_your_docs_prompt_freeze.json`).
- **Where text lives** (B2, B3, B6; the full table is under "How this seeds the multitask optimizer"). Chat-derived policy goes into `HARNESS_TASK_HEAD: ask_your_docs.*`, never into `BACKBONE`; `BACKBONE` receives only the "already shown" definition, as a rewrite that keeps its stop rule; the external heads are untouched; the tool descriptions stay one shared document with no per-task variant and no overlay key; `SERVER_INSTRUCTIONS` is hand-edited in its own $0 PR outside the ladder.
- **No new default architecture and no per-turn budget note** (Q27 supersedes Q14; M-1 refuted). `max_agent_turns` stays 12. One chat model throughout, at the Q5 pin (Round 5 amendment).
- **Larger-corpus check** (Q37(b), Q49): pydocs-mcp itself, indexed with its runtime dependencies under the Q5 embedder (embed cost printed at plan time before spending), plus 10 questions the owner writes; behaviour counts and Turns only, informational, run after final confirmation and before symptom 1 is declared solved.
- **Sizing.** Steps 0, 1, 3, 4, 5, 6 are M; step 2 (two sub-PRs) and step 7 (five sub-PRs) are M/L; the judge work is L across its tickets.

### Step 0 — capture, restart, opt-in chat trace persistence

**What changes.** An owner runbook (no repo change) and one YAML knob under `ask_your_docs` that makes the chat page launch a traced serve child and write, per answered question, a trajectory directory the `pydocs_eval` readers open unchanged.

**Runbook (Q31, owner action, tracked in the umbrella issue, not a PR criterion).** Before any restart: copy every failing question and answer out of the two running UIs on ports 8512/8513 into the step-1 slice folder as candidate held-out records; then restart both UIs on `main` at `87ac5d5b` or later; after step 2 has merged, replay the captured questions on HEAD through the step-1 vendored runner (paid; in the ledger). The replay is a spec addition beyond Q31 and Q30 step 0, which name only the capture, the restart and the trace knob: it needs the owner's go on its own, and the umbrella issue records it as an addition (captures at the pinned sha already reach the ladder at no extra cost through 1b's `query_source = OWNER` and the A/A arms; the replay exists for captures from any other corpus). If the capture does not precede the restart, the only recorded exhaustion instance is lost. The two UIs serve whatever workspace they were started on, not necessarily `example_needle@9c170b0`: a captured question enters `records.jsonl` only when its corpus is that pinned checkout and gold can be authored there; a capture from any other corpus is replayed only (behaviour counts and Turns, no gold) and never enters the dataset. The replay (ledger line 3) needs the captured questions' corpus indexed at HEAD under the Q5 embedder — the owner names the workspace, and its embed cost is the plan's printed estimate, added to that ledger line.

## Testing Decisions

A good test observes a boundary: the served system message over a real ReAct graph, the rendered tool text and `items`/`meta`, the persisted trajectory directory, the report rows, the request body a fake transport received, the label file an annotation page rewrote. Fakes are named classes (`FakeReasoningToolLlm`, `FakeRecordingGraph`, `FakeTurnFinalizer`, `NullChatTraceSink`, `FakeJevJudgeClient`, `FakeOpenRouterChatClient`, `_FakeRepoCache`, `FakeAskRunner`), never ad-hoc patches.

- **The prebuilt boundary.** The sentinel parity test and the forced-cap finalize test drive the real `create_react_agent` over a looping fake model; the raise-fake test survives only as the hand-built-graph pin.
- **The served-prompt boundary.** v3 assertions run over the message a real graph serves (`test_system_prompt_v2.py:41-53` precedent), with goldens for the no-variable render, the branch-advertised render and v2's own pin, and the seed-parity test; the candidate seed is validated by the product loader with its per-section ledger.
- **The tool-call boundary.** Wired-index tests for grep-on-file, partial `get_context`, body slots, the prose-hit pointer and read window, and the gap-free views assert the rendered text and rows plus CLI/MCP parity; description goldens regenerate once per PR that edits `descriptions.md`.
- **The trajectory boundary.** Chat trace persistence, the vendored runner's arm output and the binding's exhausted path are checked by opening the directories the `pydocs_eval` readers open.
- **The events-to-rows boundary.** New report rows are tested from fixture trajectories through `_row_of`, never through a `before_after.md` golden; the `outcome_of` truth table is pinned; the compare verb's Q10 and Q44 verdicts are pinned on fixture arms, including a runner output as one side.
- **The HTTP boundary.** `httpx.MockTransport` for the Jev client and the shared OpenRouter chat client (request goldens per role, retries, model mismatch, blind labelling with the ground-truth context and without the other label, no bearer in errors); a warm cache makes zero calls for Jev and for the escalation judge; the escalation spend cap stops calls; every external call's timeout and retry bound is asserted; the chat model's timeout, retries and provider extra body are asserted by the `ChatOpenAI` kwargs spy.
- **Byte-identity as the default guard.** Every new knob has a test that its default (or its null object) leaves the child env, the assembled prompt, the `ChatOpenAI` kwargs, the chunk tree, the source view, the arm identity or the plan text byte-identical to HEAD.
- **Freeze proofs.** The vendored records digest (re-pinned once for the chat references, before v3) and the repoqa reference file digest, the split-membership golden (`dev`, `test`, `reserved`), `ask_binding_identity()` for the citing scaffold, `delivery_map_digest()`, `TASK_SCAFFOLD_VERSION`, the external-head bytes of the candidate seed, and the three-site label and sentinel mirrors fail on any drift.
- **The role-family rule.** One test over the judge deployment YAML derives every role's family from its vendor prefix and fails when a judge, labeller or writer shares a family it must not (Round 5d, Q58).
- **The annotation boundary.** The page's AppTest (the product's `test_app_activity.py` precedent) round-trips one decision and note through the label file and asserts every other field is byte-identical.
- The full CI gate set from CLAUDE.md before every push, plus the local `benchmarks/tests` gate.
