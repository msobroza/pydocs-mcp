# Retriever-centric harness platform — skills as trainable weights — Design

**Date:** 2026-07-26
**Status:** Draft (pending owner review)
**Goal:** Reframe pydocs-mcp as two coupled platforms — a retrieval platform (the hybrid BM25 + dense + graph + late-interaction engine behind the frozen nine-tool MCP surface) and a **harness platform** (agents that consume it) — and specify the architecture that makes harness guidance a *trained* artifact: the retriever as the system's **backbone**, with a section-addressable shared **adapter** skill jointly optimized across harnesses and task types benchmarks-side, promoted into the product package through the existing publish-gate pattern (the hand-written *seed* ships as package data from P1; a *trained* revision promotes only per §8.2 decision 3), and delivered through two channels (native harness runtime and rendered server instructions / tool docs) with **zero change to the MCP tool surface**. The measurement seam that makes "trained" auditable — `harness/core/run_contract.py`'s `Trajectory` / `HarnessRunner`, with tool calls derived from the ADR 0009 trace rather than re-recorded (both land with stage 2 of `docs/superpowers/specs/2026-07-27-harness-run-contract-design.md`) — is part of the **product** package (the optimizer that consumes it is not), which is what lets a single gate, judge, and metric stack score every harness including external CLI agents.

## Abstract

The retriever is this project's core competency; harnesses are its optimized consumers. Current evidence on "grep vs. semantic retrieval" for agents is confounded exactly where it matters: the strongest recent comparison (arXiv 2605.15184) ran on conversational-memory QA with off-the-shelf harness prompts, and its own strongest finding is that the harness is a first-order variable whose effect matches or exceeds the retriever choice. The single-shot code-RAG literature (arXiv 2406.14497) shows retrieval quality carries large gains precisely where lexical overlap is weak, but is not agentic. The untested cell of the matrix is *(harness optimized for semantic retrieval) × (code tasks, measured agentically)* — and this repo already owns every ingredient to test it: a section-addressable optimizable artifact grammar, four registered optimizers, a paired-stats acceptance gate, a leak-guarded needle-search dataset, and one working harness. This spec turns those ingredients into a platform: `python/pydocs_mcp/harness/` with a harness-agnostic `core/`, the retriever as system backbone with its shared adapter skill shipped as package data like weights, multitask training arms of shape (harness × task type), and a pre-registered equal-budget falsification experiment that converts the literature's confound into a controlled variable.

## 1. Reframing: two platforms, one product

pydocs-mcp today describes itself as an indexing/search MCP server. That undersells the actual asset split:

- **Retrieval platform** — the hybrid engine (`retrieval/`, `storage/`, `extraction/`) behind the nine task-shaped tools frozen in `docs/tool-contracts.md` (ADRs 0001–0004). This is the core competency and it does not change under this design.
- **Harness platform** — everything that decides *how an agent uses* that engine: system prompts, tool descriptions, usage skills, tool-binding glue, architecture graphs. Today this exists as exactly one harness (`python/pydocs_mcp/ask_your_docs/`, 2,877 lines of Python across 28 files, plus six `.j2` templates) plus the five registered benchmarks-side optimizable artifacts (`tool_docs`, `usage_skill`, `ask_prompt`, `ask_architecture`, `retrieval_config` — all under `benchmarks/src/pydocs_eval/optimize/artifacts/`).

The reframing has one operational consequence: harness guidance stops being hand-written product copy and becomes a **trained artifact with a training pipeline, an acceptance gate, and a promotion path** — the same discipline the retriever already gets from `benchmarks/` sweeps. The nine-tool surface stays the stable interface between the two platforms; all tuning lands in YAML (`AppConfig`) or in the skill artifact, never as MCP tools or parameters (CLAUDE.md §"MCP API surface vs YAML configuration").

## 2. Evidence, honestly

### 2.1 arXiv 2605.15184 ("Is Grep All You Need?") — what it shows and what it cannot

The paper compares grep vs. vector retrieval across four harnesses (one custom research harness + three provider-native CLI coding agents from widely used vendors, unnamed here per doc policy) on **LongMemEval**, a 116-question conversational-memory QA subset — multi-session chat transcripts, not repositories, not source code. Key facts that bound its transfer to us:

- **The harnesses were not optimized for the retrieval tool.** The same wrapper scripts and prompts serve both arms; the CLIs run their stock vendor system prompts and stock tool descriptions; the vector tool's embedding model, chunking, and top-k are unreported. Any "vector underperforms" reading is a claim about an *untuned* vector tool behind an *untuned* prompt, dispatched via a generic bash wrapper in three of four harnesses.
- **The corpus maximally favors substring matching.** The authors observe that answers usually hinge on verbatim spans, and explicitly name "code semantics" among domains "where evidence is rarely literal" and where "dense retrieval and hybrid routing may look different". They state: "We do not claim that grep 'beats' vector in general".
- **The result is fragile to result delivery.** Grep wins all 10 inline cells, but under file-based delivery vector wins 5 of 10 — the retriever did not change, only how hits were rendered into context. In the distractor-robustness sweep, vector beats grep at nearly every distractor level for four of the five base models *inside the harness the authors controlled* (the fifth stays grep-ahead at most levels).
- **The harness effect is as large as the retriever effect.** Swapping harness at fixed base model moves grep-inline accuracy by up to −28.4 points; the grep-vs-vector inline gap averages ~10. The authors' own framing: "retrieval in Table 1 is really retrieval-plus-orchestration" and "a harness is not passive infrastructure".

We do **not** call the paper fallacious. Its central finding — the harness is a first-order variable that dominates or matches the retriever choice — is exactly the motivation for this design. What the paper leaves untested is the key cell: a harness *optimized for* semantic retrieval, evaluated on code tasks. Off-the-shelf agent harnesses inherit LLM tool-choice priors shaped by fine-tuning exposure to shell idioms; an un-optimized harness therefore systematically underuses a semantic retriever. Measuring the retriever through such a harness measures the prior, not the tool.

### 2.2 arXiv 2406.14497 (CodeRAG-Bench) — retrieval helps code when retrieval is good, but it is not agentic

- Dense retrievers beat BM25 exactly where lexical overlap is weakest: ODEX NDCG@10 is 6.7 (BM25) vs 37.1 (7B dense) — a 5.5× gap. The ordering inverts on repo-level RepoEval (BM25 93.2 vs 83.8) where identifiers are shared verbatim. The controlling variable across both papers is **lexical overlap between query and evidence**, not "grep vs vector".
- Retrieval quality translates to generation gains where it is high: canonical context is worth +15 to +63 pass@1 on basic programming and +8 to +16 on repo-level; on RepoEval open retrieval, the local same-repo source with a strong embedder gains +24.7 over baseline while every non-local source lands at or below baseline.
- Two caveats we inherit as design constraints: models plateau at ~5 retrieved documents regardless of nominal context window (precision at small k binds, not recall), and weaker generators gain more ("the less familiar the model is with the domain, the more the model benefits").
- **It is single-shot RAG.** One retrieval, one generation. No tool choice, no query reformulation, no multi-turn repair — none of the harness dynamics Paper A shows dominate.

### 2.3 The gap this project fills

Paper A: agentic, wrong corpus, untuned harness. Paper B: right corpus, tuned retrievers, not agentic. The cell neither tests — *co-optimized harness guidance + tuned retriever, measured agentically on code tasks* — is the cell this repo is uniquely positioned to fill: we own the retriever, the harness, the optimizer stack, and a leak-guarded code-QA dataset (`benchmarks/src/pydocs_eval/datasets/crosscommitvuln.py`). Section 6 specifies the experiment.

## 3. Thesis: skills and prompts are the trainable weights of a harness

A harness = the tool set it binds (`tool_names`, a subset of the frozen nine carried as **data** — the §6 arms differ only in this tuple while the server always serves all nine) + model + a `HarnessRunner` implementation that turns one sample into a `Trajectory` (§4.5(4); the port lands with stage 2 of `docs/superpowers/specs/2026-07-27-harness-run-contract-design.md`) + **guidance text** (system prompt, tool descriptions, usage skill, delivered per the harness's declared section→channel map). Tool set, model and runner are fixed per arm; the guidance text is the free parameter, and everything needed to train it already exists in embryo:

- The **section-addressable artifact grammar** (`python/pydocs_mcp/application/description_source.py`) — 11 canonical sections behind a closed header regex, one-normalization-pass idempotence, hash-folded `RENDERER_VERSION`, and a documented header-widening protocol (docstring lines 22–32) that is precisely the extension point an adapter/head section kind uses.
- The **bijective GEPA candidate view** (`benchmarks/src/pydocs_eval/optimize/candidates/candidate.py:53`) — each section is a GEPA component, buying per-section mutation and component-wise merge for free (ADR 0017: "The 11-section candidate buys per-section mutation targeting").
- The **validity firewall** (`optimize/candidates/firewall.py`) with the proven "firewall-accepts ⇒ product-accepts" parity rule, two universes, ~96 µs per check — invalid candidates cost zero rollouts.

**System layering (the owner's framing, adopted throughout):** the **backbone is the retriever itself** — the one shared component every task and every harness runs through. It is trainable in its own parameter space: `AppConfig` YAML (fusion weights, graph expansion, rerank steps, embedder identity), already first-class benchmarks-side as the `retrieval_config` artifact family and the `config_search` optimizer. The frozen nine-tool surface is the backbone's stable API. On top of it sits the **shared adapter**: the search-guidance skill that teaches an agent to drive the backbone — query decomposition, when `search_codebase` vs `grep`, when to stop searching and read, how to spend the ~5-document precision budget of §2.2 — optimized **jointly (multitask) across harnesses and task types**. Per-harness and per-task-type sections are **heads**, optimized on homogeneous batches. This mirrors representation learning: the backbone carries the shared representation, the adapter carries transferable retrieval *policy*, heads carry harness- and task-local conventions. The adapter is where the grep-favoring tool-choice prior gets retrained; §5.6 specifies how the two trainable spaces — backbone configs and adapter text — are optimized together without a combinatorial joint search. The stance is deliberately analogous to data-centric AI's shift of attention from model architecture to data quality: **retrieval-centric** harness work shifts attention from hand-crafted prompts to the retrieval backbone and its trained guidance.

## 4. Architecture

### 4.1 `python/pydocs_mcp/harness/` — the namespace (P0, decided)

A new top-level package `python/pydocs_mcp/harness/` becomes the home of all agent harnesses. **First move: `ask_your_docs/` relocates under it** as `harness/ask_your_docs/`. The relocation is specified in its own plan doc, `docs/superpowers/plans/2026-07-26-harness-reorganization.md` (decided; breaking rename of the console script and extra to harness-scoped names, no compat shim — see §9). Three properties the move must preserve, each verified directly against the cited files:

- The mypy exclusion (`pyproject.toml:283-293`) and coverage omit (`pyproject.toml:224-232`) both rest on "nothing in the core imports it" — the relocated path keeps that invariant; the exclude/omit globs update to the new path.
- The maturin package-data include for prompts must be fixed **in the same change**: the current glob `python/pydocs_mcp/ask_your_docs/prompts/*.j2` (`pyproject.toml:201-209`) is one level too shallow — every shipped template lives in `prompts/shared/` or `prompts/inline/`, so built wheels currently ship zero templates (editable installs mask it). The P0 include is the plan's exact literal, `"python/pydocs_mcp/harness/ask_your_docs/prompts/**/*.j2"` (the plan doc is normative for P0, and its wheel spot-check gate expects that string). `harness/core/` gained packaged prompts the same day (the shared pool, owner decision), covered by a second **explicit** include `"python/pydocs_mcp/harness/core/prompts/*.j2"` — two verifiable literals instead of the speculative `harness/**/prompts/**/*.j2` widening, whose zero-directory `**` semantics would otherwise need a wheel build to prove.
- The extra's lazy-import discipline (PEP 562 shim, function-local langgraph imports in `architectures/*.build()`) moves verbatim.

**Extraction is staged, not big-bang** (YAGNI): P1 extracts only the rows the skill-artifact loader and the eval binding actually consume — the loader, the prompt namespace resolver, the prompt-override seam, and the extra guard — **plus the two seams above, which are new modules rather than extractions and land with the run contract.** The remaining rows keep their classification here but move only when a second harness (or the loader itself) needs them; classifying now and moving later costs nothing and avoids speculative churn.

**Dependency rule (hard):** `core` never imports a concrete harness; harnesses import `core`. This is the same one-way rule the config layering already enforces (schema imports nothing from the harness, §4.3) and the same shape as `storage/protocols.py` vs `Sqlite*` adapters. Ask-your-docs-SPECIFIC code (Streamlit app, graph page, theme, CLI subprocess shape) stays inside `harness/ask_your_docs/` — the boundary runs along the module-level-`import streamlit` frontier. The graph explorer's Streamlit-free domain layer, `graph_service.py` and `model.py`, is classified SPECIFIC too: both are core-installable and unit-tested (the coverage comment at `pyproject.toml:229-231` singles out `graph_service`), but they serve only the graph page, so they stay with it rather than moving to `core/`.

### 4.3 Config layering: unchanged pattern

Each harness's config schema stays in `retrieval/config/<name>_models.py` and `AppConfig` aggregates — the exact `ask_your_docs_models.py` precedent (`retrieval/config/app_config.py:172-176`, sanctioned there by the YAML litmus test: "which agent architecture answers a question is A/B-testable behavior"). A second harness gets a sibling schema module + a sibling `AppConfig` field; the schema imports only pydantic, so `AppConfig` stays importable on the core install. Skill-artifact tuning knobs (which artifact revision to load, whether session-start injection is on) are YAML, per the frozen-surface rule.

**Adding harness N+1 (checklist):** (1) a directory `harness/<name>/` that imports `core` (never the reverse); (2) a sibling config schema `retrieval/config/<name>_models.py` + one `AppConfig` field; (3) an optional extra + console script only if it has a user-facing entry point, harness-scoped names per the P0 rename discipline; (4) tests under `tests/harness/<name>/`; (5) if it carries heavy optional deps, its **own** mypy-exclude and coverage-omit globs in `pyproject.toml` — the globs stay per-harness paths, never a blanket `harness/*`, because **`harness/core/` itself is inside both the mypy and coverage gates**: it is framework-free by design and must remain fully type-checked and coverage-counted; (6) a `HarnessRunner` implementation returning a `Trajectory` (`harness/core/run_contract.py`, stage 2) — the port every measured arm enters through, and the reason a new harness needs no new gate, judge, or metric code; (7) a declared **section→channel delivery map** (which guidance sections reach the agent through which channel), whose hash folds into the arm cell fingerprint so delivery mode is a recorded first-order variable rather than an implementation detail; (8) a contract test pinning its `Trajectory.tool_calls` SERVER slice against the ADR 0009 trace events for one recorded run. There is no harness registry and none is planned — harnesses are packages wired at composition roots, not plugins.

### 4.4 The optimizer stays benchmarks-side: training vs inference separation

Training never ships in the product wheel. The flow is:

```
benchmarks/src/pydocs_eval/optimize/          (training)
  optimizer (critique_refine | skillopt | gepa | config_search)
    → candidate ledger (per-sample resume, objective-hash keyed)
    → paired-stats acceptance: McNemar or Wilcoxon signed-rank (#218,
      gepa_harness/acceptance.py:136-150; continuous input =
      soft_resolve_fraction, trajectory/eval_report.py:219)
    → accepted artifact + per-section diff (optimize/artifact_diff.py:22)
python/pydocs_mcp/…                            (inference)
  accepted artifact lands as a reviewed commit to package data
```

Promotion follows the established **publish-gate pattern**: the eval package may not depend on a product seam before the product release shipping it (precedent: eval-0.2.0 blocked on product-0.5.2's `prompts=` seam, recorded in `benchmarks/pyproject.toml:94-102`). The optimized adapter follows the same discipline: the product wheel that ships revision N of the artifact is released before any eval package pins behavior to N. Optimizers propose diffs; humans land them — never runtime self-modification (2026-07-07 design, unchanged). The run contract is the next instance of the same gate, and a larger one: when the eval package replaces `AskTranscript` / `AskRunner` / the agent-track `AgentRunner` with imports of `Trajectory` / `HarnessRunner` from `pydocs_mcp.harness.core.run_contract`, its floor must name the product release that ships that module — the same release as the P0 rename if they land together, a later one if they do not. Renaming the eval-side types is free only while eval 0.2.0 is unpublished, which is precisely why the replacement happens now rather than as a deprecation.

### 4.5 The plug contract: two delivery channels for one adapter artifact

The backbone is pluggable into **any** harness through a four-part plug contract, of which ask-your-docs is the reference implementation: (1) **tool binding** — a named subset of the nine frozen tools (`tool_names`, data not architecture); anything that speaks MCP qualifies for *consumption* with zero integration work, and server-side observation of its tool calls is free because the ADR 0009 trace already captures them; (2) **guidance injection** — the shared adapter delivered through the harness's declared **section→channel delivery map**; a section the harness cannot accept raises `UndeliverableGuidanceError` rather than being silently dropped, and the map's hash folds into the arm cell fingerprint because delivery mode is a first-order variable (§2.1); (3) **corpus-scope config** — the `project`/`package`/`scope` selectors that pin what one request searches; (4) **the runtime port** — to be *measured* rather than merely served, a harness supplies a `HarnessRunner` implementation (`async run(sample, guidance_sections) -> Trajectory`, `harness/core/run_contract.py`, stage 2). External CLI agents therefore need a thin benchmarks-side runner adapter even though they need no product integration to consume the retriever. The same accepted adapter artifact reaches consumers two ways, with zero MCP surface change:

1. **Native harnesses** (in-repo, e.g. ask-your-docs) load it through the `harness/core` skill-artifact loader and fold the relevant sections into the single prompt-assembly site.
2. **External MCP clients** (widely used CLI coding agents and IDE integrations that speak MCP) receive it **rendered** into `SERVER_INSTRUCTIONS` and per-tool `TOOL_DOCS` — the slice-6 optimizable surfaces that already exist: `application/tool_docs.py:41` projects the packaged `defaults/descriptions.md`, and the function-local imports in `server.py:591` / `server.py:668` are what make attribute rebinding (and hence artifact overrides) reach the wire. During training, the benchmarks-side overlay wrapper (`optimize/_overlay_server.py:80`) serves candidate renderings without any product hook.

Channel 2 is how the shared adapter improves *every* external agent's use of the retriever without those agents installing anything: the guidance rides the MCP protocol's own instruction/description fields. One consequence is deliberately **not** treated as settled here: whether an accepted *trained* adapter replaces the hand-written `defaults/descriptions.md` for external clients by default is a step beyond the slice-6 precedent (which made these surfaces optimizable benchmarks-side only) and is listed as §8.2 decision 6 for the owner. This is also the honest answer to Paper A's delivery-mode finding — how guidance and results are rendered into the consuming agent's context is a first-order variable, and both renderings are ours to optimize.

### 4.6 Frozen surface, restated

Nothing in this design adds an MCP tool, parameter, or envelope field. The nine-tool surface of `docs/tool-contracts.md` is the platform boundary. All new behavior lands behind it: skill artifacts as package data, tuning in `AppConfig` YAML, training in `benchmarks/`. Agent-local capabilities follow the `reinspect_images` pattern (`ask_your_docs/reinspect.py:3-4`: an agent-local tool, "the nine-tool surface is untouched").

## 5. Joint multitask optimization of the shared adapter

This generalizes the section-addressable artifact design of `docs/superpowers/specs/2026-07-07-harness-optimization-design.md` — the 11-section grammar and optimizer seam, since hardened by ADRs 0005/0006 and the #215–#218 machinery — rather than replacing it.

### 5.1 Arms become (harness × task type)

The multitask machinery (#216/#217) already defines an arm as a (plan, sampler) pair (`optimize/multitask/__init__.py:6-13`) and derives task type from the `task_id` prefix (`sampling.py:80-105`; live types under `CombinedDataset`: `sweqapro` and `ccv`). This spec widens the arm key to **(harness, task_name)**. Datasets and tasks are many-to-many: a sample is identified by `record_id` + `task_name` (the `task_id` prefix convention extended to carry both, pinned by `REQUIRED_SAMPLE_KEYS` in `harness/core/run_contract.py`, stage 2), so one vendored CCV record can mint several task rows — QA, localization, why-archaeology — that share a record and differ only in task_name. The arm cell is therefore a (harness, task_name) cell **over records**, evaluated through the ask-your-docs binding (`ask_binding.py`) *and* through the external-client rendering (overlay server, §4.5 channel 2), and every paired statistic clusters at record level (§5.4(2)). The shared-fitness seam is already in place: `AskRubricFitness.sampler` (`optimize/fitness/ask_rubric.py:89`) with `StratifiedSampler.order()` putting every type at the head (`sampling.py:194-227`).

### 5.2 Backbone on stratified batches, heads on homogeneous batches

- **Adapter (shared) sections** train on **stratified** batches spanning all arms — a candidate edit survives only if it helps (or is neutral) across harnesses and task types. `StratifiedSampler` / largest-remainder allocation with the `_MIN_PER_TYPE = 1` floor (`sampling.py:294-306`, `:46`) is the batch engine.
- **Head sections** (per-harness, per-task-type) train on **homogeneous** batches (`CurriculumPlan` / `PerDatasetPlan`, `multitask/plans.py:119-197`), with mutation targeted at the owning section via the per-section candidate view. **v1 head keys are a fixed enumerated set, not an open family**: `HEAD: <harness>.<task_name>` over exactly {`ask_your_docs`, `external`} × {`sweqapro`, `ccv`} — four keys, each added to `_HEADER_RE` and to each artifact's allowed set via the header-widening protocol, so an unknown head stays firewall-rejected per artifact. The axis is the task name, not the dataset prefix; today's enumerated v1 names `sweqapro` / `ccv` name the single task framing each corpus mints and double as its record namespace; renaming or widening them is a deliberate event that lands with the first second framing. A new harness *or task name* is likewise a deliberate widening event, not config drift. Section targeting is real P3 work, not free: `FeedbackImplicatedSelector` hard-filters candidate keys to the `TOOL: ` prefix (`gepa_harness/module_selector.py:54`) and its `_fallback_section` returns the *first* key, not the implicated one — the filter must widen to adapter/head keys before heads can be mutation targets (scheduled in P3 with this section's batch composition).
- Scoring uses the per-type-weighted deterministic checks of #215 (`optimize/rubric/checks.py`: `applies_to`, `weight_by_type`, renormalization over applicable weights at `:158-164`) so a ccv-only check cannot tax usage tasks and vice versa.

### 5.3 Anti-overfit trio (greenfield — none of this exists yet)

Repo-wide grep confirms zero in-repo hits for rehearsal, patch-mode, or adapter/backbone concepts; today's defenses are static token budgets, required markers, the sha256 split, and the held-out gate. Three additions:

1. **80/20 rehearsal** — every adapter training batch reserves ~20% for tasks the current champion already solves; a candidate is rejected before acceptance stats run if its mean `soft_resolve_fraction` over the rehearsal slice drops by more than 0.05 versus the champion. Guards against the multitask failure mode where a new arm's gains cannibalize an old arm's competence. This is a **dev-side screen only** — it shapes the candidate stream during search and is never applied in the confirmatory arm, so the pre-registered decision rule (§6: alpha, delta_min, statistic, split) is untouched and no unregistered gate ever touches confirmatory data (ADR 0018's forking-paths rule).
2. **Section length caps** — already enforced (`PER_TOOL_TOKEN_BUDGET = 500`, `TOTAL_TOKEN_BUDGET = 3600` at `description_source.py:62-63`; `usage_skill` 1,500 at `artifacts/usage_skill.py:40`); the adapter artifact gets its own cap in the same style. Rationale stands as written at `artifacts/ask_prompt.py:47`: "stop the optimizer inflating the searchable region."
3. **Patch-mode edits** — mutations are expressed as per-section patches against the incumbent, not whole-document rewrites; the reflector rewrites one section at a time already (`gepa_harness/reflective.py:101-120` puts the candidate's *current section text* in `Generated Outputs`), so this formalizes the existing shape and makes the owner-review diff (`artifact_diff.py`) the native unit of change.

### 5.4 Acceptance: #218 as shipped

Candidate-vs-incumbent acceptance uses the paired one-sided tests exactly as merged: `AcceptanceConfig.statistic ∈ {"mcnemar", "signed_rank"}` (`gepa_harness/acceptance.py:76-82`), Wilcoxon over `soft_resolve_fraction` differences for continuous credit, exact-null enumeration (`metrics/aggregate.py:390-435`). The power argument for signed-rank at small n is recorded in that function's docstring (at n=13 with a +0.10 shift: McNemar ~3% power vs signed-rank ~95%). `keep_deterministic_on_skip` (`rubric/model.py:70`) removes the skipped-judge verdict cliff, and `rubric_config_hash` (`rubric/model.py:101-129`) keeps hard- and soft-verdict arms from ever resuming each other's ledger lines.

Two registrations this spec adds for multi-arm pools (wired in P3): (1) **stratified acceptance with per-slice non-inferiority** — the pooled paired statistic must clear alpha *and* no arm slice may regress beyond a pre-registered margin `delta_slice`. Scarce slices (`ccv` at today's n) lack the power to *prove* per-slice gains, but they can bound per-slice regressions — the honest form of "the adapter helps every arm". (2) **Record-level clustering** — whenever multiple task rows are minted from one underlying record (several task framings over the same CCV commit is the intended P5 data multiplier: QA, localization, why-archaeology from one vendored record), the **record, not the row, is the independent unit**: paired statistics cluster at record level, otherwise pooled n overstates power. The `record_id` + `task_name` split (§5.1) makes the record the addressable unit from the run contract onward (stage 2), so the clustering wiring lands **with it**, not later: it is a no-op while every record mints exactly one task row, and becomes load-bearing the first time a record carries two task names — with no second ledger or statistics change at that point.

### 5.6 Coordinate ascent across the two trainable spaces

Backbone configs (YAML, searched by `config_search` over the `retrieval_config` artifact family) and adapter text (searched by the text optimizers) are coupled — the best guidance depends on how the pipeline ranks, and vice versa — but a joint search over both spaces is combinatorially wasteful at this budget scale. v1 trains them by **coordinate ascent**: freeze the adapter, sweep backbone configs under the same multitask fitness; freeze the winning config, evolve the adapter; alternate. Every accepted move in either space passes the same §5.4 paired gate against the incumbent (config, adapter) pair, and the candidate ledger's objective-hash keying must fold the frozen counterpart's hash **and the arm cell fingerprint — which itself folds the harness's section→channel delivery-map hash (§4.5(2)) and the binding identity fields recorded as sibling ledger fields in the single measurement bump (§5.4)** — (P3 wiring) so cross-space resumes never mix incumbents and a delivery-mode or tool-binding change can never be mistaken for a text improvement. Known blind spot, accepted for v1: a config change that helps only under a *different* adapter is invisible to coordinate ascent — revisit joint proposals only if P5 evidence shows plateaus that alternation cannot break.

## 6. The falsifiability experiment (empirical centerpiece)

The design must be falsifiable: if an optimized lexical-only harness matches an optimized full-surface harness on code tasks, the retriever-centric thesis fails on its own terms.

**Arms (equal everything except the tool surface):**

- **Arm A (lexical)** — the same harness, same runner, with `tool_names = ('grep', 'glob', 'read_file')`. Its skill artifact is optimized for lexical search strategy.
- **Arm B (full surface)** — the same harness, same runner, with `tool_names` = all nine. Its skill artifact is optimized for the full retriever. The arms differ in exactly one data field; there is no arm-specific architecture class and no arm-specific runner.
- **Arm C (external, optional — pre-registered if run at all)** — a provider-native CLI agent entering through a benchmarks-side `HarnessRunner` adapter (§4.5(4)); its own shell tool (`Bash`) is **dropped from the bound set** so the arm compares retrieval surfaces rather than shell-vs-retrieval, and any residual client-side calls are recorded `observed_by == ToolCallObservation.CLIENT` and excluded from indexed-use gates (§5.4/§6).

**Controls:** identical base model, identical optimizer, identical optimization budget (trials *and* USD), identical training tasks, identical acceptance rule (§5.4), identical result-delivery rendering. Both arms get real optimization — this is the difference from Paper A, whose vector arm ran behind stock prompts. Tool-surface restriction is a harness-binding concern (which tools `client.get_tools()` exposes to the graph), not an MCP change — the server still serves nine tools; arm A's harness simply binds three. The controls include an identical *rendering rule* for the system-prompt tool catalogue: each arm's catalogue is rendered **from its own bound set** (`tool_names`), not from a static nine-tool list. This is a correction, not a restatement — a static catalogue would make the arms differ in prompt content as well as in binding, reintroducing exactly the confound the experiment exists to remove. The change re-pins the prompt freeze manifest (seed parity), and that cost is scheduled with it rather than absorbed silently.

**Evaluation:** held-out split of CCV-QA (`ccv/` tasks: single-repo, single-commit needle search with three-layer leak guards — index floor at `extraction/config.py:85`, query-token gate, suite sweeps) **plus** usage tasks (`sweqapro/`), interleaved via `CombinedDataset` (`datasets/combined.py:38`, any-prefix-representative round-robin). Anti-memorization gate `used_indexed_tools` applies **symmetrically to both arms** (`optimize/configs/optimize_ask_prompt_combined.yaml:32`) and reads the `observed_by == ToolCallObservation.SERVER` slice of `Trajectory.tool_calls` — equivalently, the ADR 0009 trace. Two consequences: it works uniformly for *every* harness including external CLI arms whose calls no in-repo binding can see, and client-only calls (notably `Bash`) stay visible as `observed_by == ToolCallObservation.CLIENT` while never counting as indexed use. Its limitation stands: `_INDEXED_TOOL_NAMES` counts all nine tools *including* `grep`/`glob`/`read_file` (`optimize/rubric/gates.py:32-44`), so arm A satisfies it trivially and it cannot distinguish lexical from indexed tool use. It is a did-you-touch-the-corpus groundedness gate, not an arm discriminator; if arm-discriminating anti-memorization pressure is ever wanted, that is a new benchmarks-side gate kind restricted to the six indexed tools (a `gate_registry` registration, zero MCP change).

**Metrics:** the single tested endpoint is (1) **accuracy** under the per-type check-weighted rubric, analyzed with the §5.4 paired statistics. (2) **Token cost per solved task** is reported as a *secondary, descriptive* metric only — per-task cost and wall time read from `Trajectory` (`cost_usd`, `wall_seconds`) and the ADR 0009 trace it derives from — one source for every harness, including external CLI arms with no in-repo transcript — summarized with a bootstrap CI on jointly-attempted tasks. The efficiency intuition is real (a semantic retriever should spend fewer exploration tokens per solve; Paper B's ~5-document precision budget is the mechanism), but no cost metric exists in `benchmarks/src/pydocs_eval/metrics/` today, none is pre-registered, and promoting cost to a tested co-primary endpoint would require a multiplicity correction under the single pre-registered alpha that nobody has specified. Wiring the cost estimator is a P5 deliverable; the outcome rule below keys on accuracy alone.

**Statistical constraint (binding):** the vendored CCV corpus holds 25 records today, under the 24–33 construction bound the suite pins (`benchmarks/tests/datasets/test_crosscommitvuln_vendored.py:42` asserts the *bound*, not the count — n can move within it without a test failing). The held-out partition makes the effective test n smaller still. The only power computation this repo records is the signed-rank-vs-McNemar comparison in `metrics/aggregate.py` (n=13 with a +0.10 shift: signed-rank ~95% power vs McNemar ~3%); no in-repo computation gives the signed-rank MDE at the experiment's actual held-out n — `optimize/prereg/power.py` models only the McNemar gate. Therefore: **before any paid rollout, `prereg/power.py` gains a signed-rank power function, and the MDE derived at the actual held-out n is recorded in the pre-registration** — until that number exists the experiment claims no specific detectable-effect size. **Corpus growth (P5) is the path to detecting small effects** — with the caveat that the current construction methodology is structurally capped at 33 records (§7 P5) — and the ccv+sweqapro combined pool is the higher-n secondary analysis.

**Pre-registration (all slots committed to `campaign_preregistration.yaml` before any paid rollout; the ADR 0018 loader refuses launch while any is missing; final selection then follows ADR 0020's frozen-test protocol — each arm's champion is confirmed exactly once on the frozen held-out set, never re-picked after peeking):**

| Slot | Registered value (proposed; the owner approves the budget line) |
|---|---|
| CCV partition | 10 train / 15 held-out **records** — the split is committed as `record_id` hashes before training starts, and *every* task row minted from a record travels with that record. Splitting rows would leak a record's content across train/held-out the moment a second task framing per record lands (§5.4(2)); arm training additionally draws on `sweqapro` tasks. |
| Optimizer | `gepa` (the ADR 0017 thin adapter) — the same optimizer for both arms |
| Base model | one pinned model id shared by both arms, written into the prereg at campaign start alongside the budget |
| Budget per arm | equal trials and USD for A and B; proposed cap US$40/arm from the §7 P5 cost model — this is the number the owner authorizes |
| Statistic | one-sided Wilcoxon signed-rank over paired `soft_resolve_fraction` differences, alpha 0.05 (requires the §5.5(4) prereg `statistic` field first) |
| Primary endpoint | accuracy on held-out CCV; secondaries: combined ccv+sweqapro pool, descriptive token cost |
| Gates | `used_indexed_tools` symmetric across arms, as noted above |

**Outcome interpretation:** B ≫ A on accuracy (with cost reported descriptively) → thesis supported, and Paper A's confound is demonstrated controlled. B ≈ A → the retriever's agentic value on this task distribution is not established; the honest next probe is task-distribution (needle-search may still be too lexical — CCV queries are leak-scrubbed of identifiers precisely to prevent verbatim matching, which is why they are the right instrument). A > B → a real finding against the thesis at this corpus size; publish it.

## 8. Decided vs Open

### 8.1 Decided (not re-litigated here)

- The nine-tool MCP surface is frozen; this design adds zero tools/params/envelope fields.
- The harness reorg (P0) happens, as a breaking rename with no compat shim, per its own plan doc.
- The optimizer stays benchmarks-side; artifacts promote via reviewed commits under the publish-gate ordering (§4.4).
- Acceptance statistics are the #218 pair (McNemar / Wilcoxon exact, one-sided) over ground-truth-derived scores; the ADR 0017 §8 shaped-score/acceptance separation stands.
- Section-addressable artifacts with the closed-header grammar, firewall parity, and per-section diffs are the candidate representation.
- Sample identity is `record_id` + `task_name` — the `task_id` prefix convention extended, pinned by `REQUIRED_SAMPLE_KEYS` in `harness/core/run_contract.py` (stage 2); the dataset prefix survives as the record namespace, not as the task type (this supersedes the earlier `task_id`-prefix-only typing). Record-level clustering (§5.4(2)) and record-level splitting (§6) follow from that identity. The leak-guard trio on CCV is non-negotiable.

### 8.2 Open decisions

1. **Exact identifier string for the relocated harness (script + extra).** The rename itself is decided (§8.1; plan §Decided item 4 — do not reopen); only the literal string is open, and the plan doc's §Open 1 is the **single canonical option list**, mirrored here: (a) `harness-ask-your-docs` for both script and extra — the plan's recorded lean; (b) `pydocs-harness` / `[harness]` — shorter, but semantically collides with the *eval*-harness vocabulary (`benchmarks/`, `pydocs_eval`, `AGENT_TRACK.md`; plan trap T8). **Recommendation: (a)**, as ratified-lean; the owner confirms the literal before P0 Step 3, and this spec defers to the plan on it.
2. **`harness/core` module naming.** Options: (a) `harness/core/` (mirrors the brief); (b) `harness/_shared/` (private, discourages external import); (c) `harness/runtime/`. **Recommendation: (a)** — `core` states the dependency rule ("core never imports a concrete harness") in the name; underscore-privacy is wrong because the eval harness is a legitimate external consumer of these seams.
3. **When the optimized artifact starts shipping in the product package.** Options: (a) immediately — first accepted adapter artifact lands in `defaults/` package data; (b) eval-side only until the §6 experiment supports the thesis, product ships hand-written seed until then; (c) ship behind a YAML flag defaulting to the seed. **Recommendation: (b)**, on evidence-before-shipping grounds alone — shipping a trained artifact before its headline experiment reports would put the release cart before the evidence horse; (c) violates the single-source-of-truth default rule for marginal benefit. One consequence of (b) to hold consciously: while the product carries only the hand-written seed, the publish gate (§4.4) forbids any *eval* release from pinning behavior to a trained revision — the product release must exist first. If an eval pin on the trained artifact is ever needed sooner, that need alone flips this decision to (a).
4. **Who owns rendering adapter → server instructions.** Options: (a) product — a renderer in `harness/core` produces `descriptions.md` content at build time; (b) benchmarks — the overlay wrapper (`optimize/_overlay_server.py`) remains the only renderer and the product just packages its accepted output verbatim. **Recommendation: (b) for training, (a) at promotion time** — during search the overlay stays the zero-product-hook channel; at promotion, a small product-side projection (the delimited-artifact grammar of `docs/superpowers/specs/2026-07-07-harness-optimization-design.md` §D2a already round-trips) keeps the packaged `descriptions.md` derivable from the adapter artifact so the two channels cannot drift. The parity test pins renderer output against the artifact hash. Constraint added by the delivery-map rule (§4.5(2)): whichever renderer is used is a declared entry in the harness's delivery map, and its identity hashes into the arm cell fingerprint. "Overlay during search, product projection at promotion" is therefore a change of measured configuration — legal across campaigns, never silently mid-campaign, and the promotion-time parity test pins the product projection's output against the artifact hash the campaign accepted.
5. **File-based skill delivery for external CLI agents.** Beyond channel 2 (§4.5), should the server also emit a standalone skill file (e.g. a markdown document a CLI agent loads as a project skill)? Options: (a) no — server instructions/tool docs are the only external channel; (b) yes — ship a `pydocs-mcp export-skill` CLI writing the rendered adapter to a file. **Recommendation: (a) for now** — channel 2 needs no user action and no new distribution obligation; revisit after P6 if conformance data shows external agents ignore server instructions in practice. (b) would be a CLI addition, not an MCP change, so it stays available without a versioning event.
6. **Does the accepted *trained* adapter replace the hand-written `defaults/descriptions.md` for external MCP clients, and is there a YAML opt-out?** (Surfaced from §4.5 channel 2 — the slice-6 precedent made these surfaces optimizable *benchmarks-side*; nobody has ratified "the product ships optimizer-trained text to every external client by default".) Options: (a) replace at promotion, one source of truth; (b) replace, with a YAML revision selector defaulting to the accepted revision, so a deployment can pin back to the hand-written text (deployment-level rollback, consistent with the YAML-tuning rule); (c) external clients keep hand-written text until P6 conformance data exists. **Recommendation: (b)** — promotion should reach external clients or channel 2 is theater, and a YAML rollback path costs nothing and stays inside the frozen-surface rule. One consequence to record with (b): since the delivery map's hash folds into the arm cell fingerprint (§4.5(2)), "external clients receive the trained adapter" is an experimental condition, not merely a deployment default — the YAML revision selector is therefore also the knob that pins a campaign's delivery configuration, and a deployment that pins back to the hand-written text is a different measured cell, not a rollback of the same one.
7. **Release mechanics of the P0 breaking rename.** The plan doc pins no product version and no semver stance, and the break is quieter than it looks: pip treats an unknown extra as a *warning*, so `pip install 'pydocs-mcp[ask-your-docs]'` against the renamed release yields a silently agent-less install, and the old console script simply vanishes from PATH — the break is loud only at first run. Options: (a) fold into the next routine 0.x minor with only the planned CHANGELOG entry; (b) whichever version the owner picks at release time, ship it with a README/CHANGELOG migration block (old → new install and command lines) plus an explicit note about the silent pip-warning degrade, and pin the eval floor (plan trap T9) to that release. **Recommendation: (b)** — the version number is the owner's call at release time, but the migration block and the silent-degrade warning are not optional.

### 8.3 Trained-artifact review + licensing

Optimizer-generated text ships as package data and renders into `SERVER_INSTRUCTIONS` / `TOOL_DOCS` consumed by every external MCP client, so "reviewed commit" (§4.4) gets a concrete promotion-time checklist:

- **Injection review** — the per-section diff (`optimize/artifact_diff.py`) is reviewed for instruction-injection patterns: imperatives addressed to the consuming agent beyond retrieval guidance, links or URLs, claims about tools that do not exist on the nine-tool surface, and text at or over the section caps (§5.3(2) makes the caps mechanical; the rest is the human reviewer's explicit brief — the author of this text is an LLM optimizing a metric, and the review threat model must assume that).
- **Provenance + license** — accepted artifact text ships under the project's own license like any other committed file; the promotion commit records which optimizer and model produced the revision (the candidate ledger already keys this), and the model provider's output terms are checked once per provider at first promotion.
- **CCV corpus licensing** — the vendored records carry the CC BY 4.0 attribution NOTICE + change statement specified in `docs/superpowers/specs/2026-07-24-crosscommitvuln-qa-dataset-integration-design.md` §4.2 (packaged into wheel *and* sdist as a release gate); P5's second-source growth must satisfy the same attribution discipline before any new record is vendored.

Anything this checklist cannot resolve at promotion time goes to §8.2 as a new open decision — it does not ship.

## 9. Non-goals

- **No new MCP tools, parameters, or envelope fields** — restating §4.6; behavior tuning goes to YAML/AppConfig.
- **No compat shim** for the old `ask-your-docs` script or `[ask-your-docs]` extra names — the P0 rename is breaking by decision.
- **No rename of the `pydocs-mcp` distribution** — package name, module name, and entry point are untouched.
- **No harness marketplace / third-party harness registry speculation** — `harness/` hosts this repo's harnesses and there is no plugin registry. External agents are *served* through channel 2 only; when one is *measured* as an experiment arm it enters through a benchmarks-side `HarnessRunner` adapter (§4.5(4)) that lives in `benchmarks/` and is observed through the ADR 0009 trace — never as a registered product-side harness.
- **No `TaskEnvelope` / `HarnessTask` type, no capability enums, no `TaskHarnessBinding` (the full Bridge), no runtime protocol for non-LangGraph toolkits, and no public `HarnessBuildSpec` API** — each is deliberately deferred, and each is a drop-in *behind* the existing port rather than a redesign of it: `HarnessRunner.run` takes a `Mapping` sample validated against `REQUIRED_SAMPLE_KEYS`, so a typed envelope can replace the mapping later without moving the seam, and `build_agent`'s keyword parameters stay harness-private for the same reason. Building any of them before a second non-LangGraph harness exists is speculative generality.
- **No runtime self-modification** — optimizers propose, humans land (2026-07-07 design, unchanged).
- **No detectable-effect-size claim for the §6 experiment** beyond what the pre-registered signed-rank power computation (§6) establishes at the actual held-out n — small-effect detection waits on P5 corpus growth.
